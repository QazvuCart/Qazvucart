# QazvuCart V1 (Angular + Express + PostgreSQL)

Status: Phases 1-5 built (foundation, design system, storefront, admin, WhatsApp ordering). Phase 6: automated tests and a hardening pass are in; a full manual pass on a machine with network access is still required (see "Phase 6").

## Setup
1. Requirements: Node 20.19+ or 22, PostgreSQL 14+.
2. `npm run install:all`
3. `cp api/.env.example api/.env` and fill in `DATABASE_URL` and `SESSION_SECRET` (`openssl rand -hex 32`).
4. Create the database: `createdb qazvucart`, then `npm run migrate`.
5. Terminal 1: `npm run dev:api` (port 4000). Terminal 2: `npm run dev:web` (port 4200, proxies /api).
6. Production build: `npm run build`.

## Layout
- `api/` Express + Drizzle. `migrations/*.sql` is the schema source of truth (applied by `src/db/migrate.ts`). `src/db/schema.ts` mirrors it for typed queries.
- `web/` Angular 19 standalone app, Tailwind v4 tokens in `src/styles.css`.

## Design decisions
- Money is integer paise (`price_minor`). A NULL price means the product cannot be ordered.
- The database starts empty. No seed data.
- Public API returns only customer-facing fields of active, non-archived products.
- Future multi-vendor: add a nullable `vendor_id` to `products` later; no marketplace code in V1.

## Phase 3: storefront
- Routes: `/`, `/products` (search, category, sort via query string), `/categories/:slug`, `/products/:slug`, `/about`, `/contact`, `/policies/:slug`.
- Server-side rendering is on. Production: `npm run build`, then `npm run start:api:prod` and `npm run start:web:prod`.
- Web server environment variables: `API_ORIGIN` (default http://localhost:4000), `PUBLIC_SITE_URL` (default http://localhost:4200, used for sitemap and Open Graph URLs), `WEB_PORT` (default 4200).
- `/sitemap.xml` and `/robots.txt` are generated by the web server from real products only.
- About, contact and policy text come from `site_settings` keys: `about_content`, `contact_email`, `contact_phone`, `contact_address`, `instagram_url`, `whatsapp_number`, `policy_shipping`, `policy_returns`, `policy_privacy`, `policy_terms`. Until the admin screen exists (Phase 4), add them with SQL. Empty policies show a clearly marked draft notice.
- The product page validates required options and computes totals in integer paise. The WhatsApp order form is described under Phase 5.
- `comparison_price_minor` is stored but not shown: no discount or reference price is displayed in V1.

## Phase 4: admin
### Create the admin account
```
cd api
ADMIN_EMAIL=you@example.com ADMIN_PASSWORD='a long passphrase of 12+ characters' npm run create-admin
```
Run it again with a new password to reset it. Then open `/admin/login`. Sessions last 8 hours.

### Cloudinary setup
1. Create a free account at https://cloudinary.com and copy the cloud name, API key and API secret from the dashboard.
2. Put them in `api/.env` (`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`). The secret never leaves the API.
3. Uploads use **server-signed** uploads, not an unsigned preset. An unsigned preset lets anyone who finds its name upload to your account; a signed upload needs a signature that only a logged-in admin can request. The signature fixes the folder (`CLOUDINARY_FOLDER`) and the allowed formats (jpg, png, webp). The 8 MB limit is checked in the browser, and again by the API, which asks Cloudinary for the real size and format when a product is saved and deletes oversized files.
4. Images removed from a product, or belonging to a deleted product, are deleted from Cloudinary only if no other product still uses them. Images uploaded in the form but never saved stay in Cloudinary until you remove them there.

### Admin security
- Passwords are hashed with Argon2id. Sessions are random tokens stored hashed in the database, in an httpOnly, SameSite=Strict cookie (Secure in production).
- Every write needs an `x-csrf-token` header that is derived from the session, and every admin route checks the session on the server.
- Login is limited to 10 failed attempts per 15 minutes per IP. The admin area is rendered in the browser only and is marked noindex.
- Behind HTTPS in production, set `NODE_ENV=production` so the cookie is Secure.

## Deploying on Render
Create a PostgreSQL database, then two Web Services from this repo.

**API service** (Root Directory `api`)
- Build: `npm install --include=dev && npm run build`
- Start: `node dist/db/migrate.js && node dist/server.js`
- Env: `NODE_VERSION=22`, `NODE_ENV=production`, `DATABASE_URL` (internal URL), `SESSION_SECRET`, `CLOUDINARY_*`, optional `WHATSAPP_NUMBER`, `INSTAGRAM_URL`.

**Web service** (Root Directory `web`)
- Build: `npm install --include=dev && npm run build`
- Start: `npm run serve:ssr`
- Env: `NODE_VERSION=22`, `API_ORIGIN` (the API's internal URL, e.g. http://qazvucart-api:10000), `PUBLIC_SITE_URL` (the public https URL).

Create the admin once from the API service's Shell: `ADMIN_EMAIL=you@example.com ADMIN_PASSWORD='long passphrase' node dist/scripts/create-admin.js`

## Phase 5: WhatsApp ordering
There is no payment gateway and no order storage. The product page collects the order, builds a message and opens `https://wa.me/<number>?text=<encodeURIComponent(message)>`.

- **Configuration:** set the number in Admin > Settings (`whatsapp_number`, digits with country code, e.g. `919876543210`) or in `WHATSAPP_NUMBER` in `api/.env`. The admin setting wins. With no number configured, the order form says ordering is unavailable. Nothing is invented. Instagram is a secondary contact (`instagram_url` / `INSTAGRAM_URL`, https only).
- **Button is enabled only when:** the product has a price, every variant group has a choice, and quantity is 1-99. Name, phone (7-15 digits), delivery address (10+ characters) are validated when the button is pressed; errors are shown and nothing opens.
- **Location (optional):** paste a Google Maps link (https; google.com/maps, maps.google.com, maps.app.goo.gl accepted) or press "Share my location". The browser asks permission only after that press; if denied, the customer is told to paste a link or leave it empty. The coordinates are placed in the visible field as a Maps link so the customer sees exactly what is sent.
- **Message:** `QAZVUCART — ORDER REQUEST` with name, phone, product, product ID, product URL, variant, size / phone model, quantity, unit price (base + selected variant extras), subtotal, address, Maps link, customisation details, and the closing request to confirm availability, delivery charges, payment instructions and acceptance. Money is integer paise. Customer text is stripped of control/invisible characters, length-capped, and multi-line values are indented so they cannot imitate another field. The message is shown for review before sending.
- **After pressing the button:** WhatsApp opens in a new tab and the page shows "Your order request is ready in WhatsApp. Send the message to contact QazvuCart. Our team will confirm availability, delivery charges and payment instructions there." A link reopens WhatsApp if the pop-up was blocked. No confirmation is faked.
- **Instagram:** cannot pre-fill messages, so the page offers "Copy request text" plus a link to the profile.
- **Custom images:** there is no customer image upload (it would need storage and moderation that V1 does not specify). The customisation box tells customers to send their image in the WhatsApp chat.
- **Privacy:** customer details are never sent to the API or stored; they exist only in the browser and in the WhatsApp message.

## Phase 6: testing and hardening
### Automated
- `npm --prefix web test`: 13 unit tests for money handling, validation, Maps-link allow-listing, message content, field-forgery protection, URL encoding round-trip, and missing-price/number handling. Needs only Node 22.18+ (no installs).
- `API_URL=http://localhost:4000 npm --prefix api run test:smoke`: black-box checks against a running API on an empty database: empty catalogue, 404s, input validation, settings whitelist, every admin route returns 401 anonymously, forged cookie, login error wording, headers, no leaked internals.
- Migration check: `api/migrations/0000_init.sql` applies cleanly to PostgreSQL 16, creates no rows, and rejects negative prices.
- Hardening added: rate limit on `/api/admin/uploads/sign` (30/min).

### Manual checklist (run once before launch)
1. `npm run build` succeeds; start both services.
2. Empty catalogue: home, `/products` show empty states, no placeholder products.
3. Admin: log in; create a category; add a product (price, variants, 2 images); confirm it appears on `/products`; edit it; deactivate, archive, delete (confirmation shown); confirm the Cloudinary files are removed.
4. Upload a `.gif`, a `.pdf` and a file over 8 MB: all refused.
5. Product with no price: shows "Price not set yet" and the order button is disabled.
6. Order flow on a phone (Android and iPhone): choose options, fill details, Share location (allow once, deny once), review, press the button, check that WhatsApp opens with the right text and the confirmation appears.
7. Visit `/admin` logged out: redirected to login; `curl /api/admin/products` returns 401.
8. Stop PostgreSQL: public pages show the error state, not a stack trace.
9. Check for horizontal scroll at 360px width.

## Design update — animated spatial storefront
The storefront has been updated with a broader creative-commerce identity rather than being positioned only around posters and phone cases.

- The home hero uses a self-contained CSS 3D composition (orbits, layered discs, floating tiles, cubes and spheres). It does not require product records or product photography to render.
- The homepage collection area is populated from active categories returned by the API. It does not invent category names or show empty categories as available collections.
- The featured product grid continues to use real Cloudinary product images. If an image is absent, it shows a clearly abstract decorative placeholder rather than fabricated product photography.
- Product cards include restrained 3D pointer tilt, image zoom and hover elevation. Motion is reduced when the visitor has `prefers-reduced-motion` enabled.
- Brand copy is now broad enough for additional lifestyle and personalised product categories. Categories and product variants remain administrator-managed; no example categories or products are seeded.
- Ordering remains WhatsApp-only. There is no payment gateway, online payment state or automatic order confirmation.
